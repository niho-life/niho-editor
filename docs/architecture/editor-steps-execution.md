# 手順（#37）の実行基盤：方式の選択肢と推奨

状態: **方式は B（editor 専用）に決定**（オーナー 2026-10-31）。Issue #37、設計 [editor-niho-life-design.md](editor-niho-life-design.md) §7.2。この文書は「画面を閉じても進む実行」をどこで・どう動かすかの方式と、B の設計案。コードは含まない。

## 1. 決めたいこと

手順（記事制作・議事録・インサイト整理）の各段階を、次の 2 つの受入を満たして実行する基盤の方式。

- 手順の途中で画面を閉じても進み、戻ると帯が最新。失敗した段階だけやり直せる。
- 上流を直したときに下流へ印（前提変更）が付き、再実行で消える。

## 2. 要件

| 要件 | 内容 |
| --- | --- |
| 閉じても進む | ブラウザに依存しない。サーバー側で実行する |
| 二重に実行しない | 同じ段階を同時に 2 回走らせない。実行する側が落ちても、あとで安全に再開できる |
| 失敗した段階だけやり直す | 成功済みの上流は再利用する。「作り直す」はその段階から |
| 前提変更 | 上流のページが直されたら、下流の段階に印を付ける（基準の比較） |
| 結果はふつうのページ | 各段階の結果はフォルダ直下の役割ページのタブ（#309。それより前は録音のサブページ）。ページの正本は editor の DB |
| 費用と許可 | AI の費用に上限を置ける。誰がどれだけ使うかを止められる |
| 公開境界 | 鍵・認可・実データは非公開（[publication-gates.md](../security/publication-gates.md)）。公開 CI から本番へ配備しない |

## 3. すでにあるもの

- **docs-core（公開）**: 手順のテンプレート（記事制作／議事録／インサイト整理）、段階の「基準」とその比較で前提変更を判定する部品、段階の状態の言葉。**足りない**のは「ここから作り直す」（段階の配列を index で切る数行）と、画面側の段階の状態の型（いまは `済み・作成中・待機` で、設計の `失敗`・`前提変更` が無い）。
- **非公開の NIHO API の遠隔実行（NIHO docs）**: 録音ページの工程を Run・Step・Attempt として受け付け、実行側が claim と生存確認（heartbeat）で実行し、許可と予算を検査して結果を確定する仕組みが実装済み。ただし対象は **NIHO docs のクラウド保管庫のページ**で、editor のページ（別の DB）を直接は扱わない。
- **editor 側（#46・#33・#38）**: ページの正本、版（`ai` の理由を含む）、`pages.parent`・`pages.recipe`・`pages.step_status`（済み・作成中・待機・前提変更）、AI のモデルの接続口（#38）。

## 4. 選択肢

- **A. NIHO の遠隔実行に載せる**: editor は受付と表示だけ。実行・予算・許可は既存のものを使う。
- **B. editor 専用の実行基盤**: Cloud Tasks と、同じサービスの内部の route（OIDC を自分で検証）を editor の側に作る。
- **C. 併用**: 実行の制御は B、AI の呼び出しと予算は NIHO の既存の仕組みに委ねる。

| 観点 | A | B | C |
| --- | --- | --- | --- |
| 閉じても進む・再開 | 既にある | 新しく作る（§5） | B と同じ |
| 失敗した段階だけやり直す | 既にある（段階の再取得） | 新しく作る | B と同じ |
| 予算・許可 | 既にある | 持たない。当面は #38 の使用量と上限で代える | 既存を使う |
| ページの正本 | 二重になる（保管庫と editor）。入力と結果の受け渡しが要る | **editor の DB 1 つ**。サブページの作成と段階の状態を同じ transaction で書ける | 受け渡しが要る |
| #45 の移行との関係 | 保管庫を移行する間、二重の正本が長引く | 保管庫を移行しても影響なし | A に近い |
| 非公開側の作業 | **必要**（editor の入力・結果を扱う契約の追加、リリースが非公開側に縛られる） | 不要 | 必要（AI と予算の口） |
| 追加の費用 | ほぼ無し | 小さい（§5） | A と B の間 |
| 実装量 | 小（受付と表示）＋非公開側 | 大（実行制御） | 中〜大 |

## 5. 決定: B（editor 専用）。AI の呼び出しは接続口の向こうに置き、C への道を残す

理由は 3 つ。(1) **ページの正本が 1 つ**で、段階の確定とサブページの作成を同じ transaction で行えるので、「閉じても進み、戻ると帯が最新」の整合を保ちやすい。(2) editor の出荷が非公開側のリリースに縛られない。(3) #45 の移行（保管庫 → editor）と独立に進められる。費用と許可の機能は B には無いが、#38 の使用量と月の上限で当面を代え、あとで接続口の向こうに NIHO の予算の口を足せる（C）。

### 5.1 データ（案）

- `step_runs`: id・owner・親（**フォルダ**。#309。それより前は録音ページ）・入力のタブ（`input_tab`・`input_revision`）・テンプレート（recipe）・状態（queued／running／succeeded／failed／canceled）・開始の段階（`from_step`）・作成と終了の時刻。
- `step_attempts`: run・段階の index・**世代（generation）**・状態・lease の期限・生存確認の時刻・エラーの種類（短い code だけ）・結果のページ・入力の基準（hash）・資料を上限で切ったときに使った字数（`input_used_chars`。切っていなければ NULL。#277）・区切りの状態（`chunk_count`・`chunk_index`・`chunk_blocks`・`chunk_basis`。区切らない段階は `chunk_count` が NULL。§5.7）。
- `pages.step_status` に `failed` を足す（migration）。`pages.parent`・`pages.recipe` は既にある。

### 5.2 実行（案）

1. 受付の API が run を作り、最初の段階を Cloud Tasks に積む。task の名前は `run + 段階 + 世代` で、重複した積み込みを無視する。
2. **同じサービスの内部の route**（`/api/internal/steps/run`）が段階を実行する。サービスは誰でも呼べる設定なので、route が **Google の ID トークン（OIDC）を自分で検証**し、Cloud Tasks が付ける身元（専用のサービスアカウントのメール・audience が worker の URL）だけを通す（通らなければ本文を読まずに 401）。(a) **claim**（世代を 1 つ進めて lease を取る）(b) 入力の基準を確定 (c) AI を呼ぶ (d) **サブページの作成（id は run と段階から決定的に作る＝再実行しても同じページ）と段階の状態の確定、そして次の段階を `queued` にすること（積む意図の記録）を 1 transaction で**書く (e) `queued` になった次の段階を Cloud Tasks に積む。積む前に worker が落ちても、`queued` の状態が残るので、手順が止まったままにならない（5 で拾う）。
3. 世代が古い worker の確定は拒否する（取消・再取得のあとに遅れて返ってきた結果で上書きしない）。
4. **失敗**: 入力の誤り（4xx 相当）はすぐ `failed`。一時的な失敗（5xx・時間切れ）は、段階の試行を runner が数えて 3 回まで積み直す（指数的に間隔を空ける）。上限を超えたら `failed`。キューの再試行（`max-attempts` 5）は、worker が claim の前に 200 以外を返した HTTP の失敗のためのもの。
5. **再開**: Cloud Scheduler の定期の掃除（5 分おき）が、次の 2 つを拾って積み直す。(1) worker が落ちて lease が切れた `running` の段階（世代を進めて積む）。(2) 一定の時間を過ぎても claim されない `queued` の段階（確定のあと、次の段階を積む前に worker が落ちた・task が失われた場合）。どちらも task の名前が `run + 段階 + 世代` で決まるので、すでに積まれていれば重複は無視される。
6. **取消**: 世代を進める。実行中の worker は確定のときに拒否される。

### 5.3 前提変更と作り直し

上流のページが直されたら、下流の段階の「入力の基準」が変わる。docs-core の基準の比較を流用して、下流の `step_status` を前提変更にする。「作り直す」は、その段階から新しい run（`from_step`）を作る。成功済みの上流は再利用する。

### 5.4 画面への反映

- 各ページの上の帯は、`GET /api/pages/{id}/steps` を数秒おきに読む（Server-Sent Events は後で）。サイドバーの「進行中」の印は `pages.step_status` が作成中の行。
- 終わったときの通知は、ブラウザ通知（許可したときだけ）。画面を閉じている間の通知（Web Push）は後。

### 5.5 費用（見込み）

Cloud Tasks は月 100 万回まで無料。worker は Cloud Run の min 0 で、使った分だけ。Cloud Scheduler は 1 件で月 15 円ほど（NIHO finance の見積は 3 件で約 45 円）。AI の費用は #38 の使用量と上限で見る。共有 Cloud SQL に表が増えるが、固定費は増えない。

### 5.6 制約

- 1 つの段階は続きの要求も含めて動く。Cloud Tasks の上限は 30 分だが、実行器は 24 分で新しい AI 要求を止め、残り 6 分を結果保存と終了処理に確保する（#225、未マージ・未配備）。長い録音の文字起こしは #36 の別経路（音声の取り込みと文字起こしの状態）で、この基盤の段階には含めない。
- B には**予算・許可の仕組みが無い**。上限を超えた利用を止めるのは #38 の使用量の判定だけ。
- 長い入力の全文を書き直す段階は、1 区切りを 1 回の claim で処理する（§5.7）ので、1 回の task は区切り 1 つ分（約 1.6 万字の書き直し）に収まる。

### 5.7 長い入力の区切り（#277）

全文を書き直す段階（手順の段階の `chunked` が ON）で、書き直す対象が 18,000 字を超えたときの進み方（区切り方そのものは
[editor-steps-recipes.md](editor-steps-recipes.md) §2.8「長い入力を区切る」）。**段階の attempt は 1 つのまま**（`step_attempts` の
主キーは変えない）で、attempt が区切りを順に進む。**1 区切り = 1 回の要求 = 1 回の claim**。既存の世代・lease・CAS・取消・掃除の保証を
そのまま使う。

**列**（migration `20261106211229_steps_chunks`。追加だけ）:

| 列 | 意味 |
| --- | --- |
| `chunk_count` | 区切りの数（1〜60）。区切らないなら NULL |
| `chunk_index` | 終えた区切りの数（＝次に処理する区切りの番号。0 始まり。`chunk_count` 未満） |
| `chunk_blocks` | 終えた区切りごとの出力ブロックの配列の配列（長さ = `chunk_index`）。入りかけの出力に `partial_blocks` は使わない |
| `chunk_basis` | 最初の区切りを始めたときの入力の基準（`computeStepBasis` 全体の sha256） |

**状態遷移**（runner。`apps/editor-web/src/steps/runner.ts`）:

1. claim（世代 +1・lease。`chunk_*` は消さない）→ `readStepInput`。
2. 段階が `chunked` で対象が 18,000 字超なら区切りの道。最初（`chunk_count` が NULL）は区切りを計算して `startChunks`
   （世代と `chunk_count IS NULL` で fence）で数と基準を記録する。60 を超えれば非再試行の `input_too_long`。
3. 2 つ目以降は、今の入力の基準が `chunk_basis` と違えば（文字起こしの編集など）**次の区切りの前に止めて**非再試行の `input_changed`。
4. 区切り `i` を実行器へ（`chunk: { index, count, text, previousTail }`）。
5. 途中の区切りは `commitChunk`: 世代・状態・`chunk_index` の CAS で `chunk_blocks` に追記して `chunk_index` を進め、attempt を
   `queued` に戻して lease を外す（`tries` は 0 に戻す。再試行の上限は区切りごと）。runner が `<run>-<段階>-<今の世代>` の名前で
   同じ段階の次の区切りを積む。サブページの本文は書かない。
6. 最後の区切りは、終えた区切りの出力と順につないで**既存の `commitAttempt`** で 1 版にする（`inputBasis` は今まで通り `computeStepBasis`）。

**失敗**: 既存の `failAttempt`（`tries`・再試行の間隔・`MAX_TRIES`）のまま。**失敗した区切りだけを繰り返し**、終えた区切りは保つ。
lease 切れの掃除（`sweepExpiredLeases`）・積み直し（`requeueAttempt`）も `chunk_*` を消さない。attempt が**最終的に失敗**したとき
（再試行を使い切った・非再試行・lease 切れで使い切った）は、`chunk_blocks` をつないだもの＋今の区切りの書けたところまでを
`partial_blocks` にも残す（既存の「途中までの出力を確認」がそのまま効く）。

**やり直し（resume）**: `POST /api/pages/{id}/steps/runs/{runId}/resume`（認可・same-origin 検査は他の steps API と同じ）。
`resumeRun`（`packages/editor-store/src/step-runs.ts`）が親 → run の順に lock し、1 transaction で次を確かめてから戻す。

- 本人のその親ページの run でなければ 404。進行中の run があれば 409 `run_in_progress`（`step_runs_active_idx` の競合も同じ）。
- 最新の run でない・失敗していない・失敗した段階が `chunked` でない（区切りを始めていない）・結果のページが無いなら 409 `not_resumable`。
- 入力の基準が `chunk_basis` と違えば 409 `input_changed`（最初から作り直す）。
- 通れば同じ run・同じ attempt を `failed → queued`（`tries` 0・世代 +1・`chunk_*` は保つ・`partial_blocks` は消す）、後続の
  `canceled` を `pending`、run を `queued` に戻し、`<run>-<段階>-<新しい世代>` で積む。積めなくても attempt は `queued` のまま残り、
  定期の掃除が積み直す（取消すと続きからやり直せなくなるので取消さない）。

**帯**: `RunView.steps[].chunk = { index, count }`（待ち・実行中・失敗のときだけ。`index` は終えた数）。区切りの合間の `queued` も
作成中として「作成中 3/5」（分子は今処理中の番号）。失敗は「区切り 3 で失敗」と「区切り 3 からやり直す」（`input_changed`・
`input_too_long` では出さない）。

手順の定義（`recipes`）をどこに置くか・手順を作る画面・旧 NIHO docs の工程設計から引き継ぐ振る舞いは
[editor-steps-recipes.md](editor-steps-recipes.md)（#37 T4）。

## 6. 進め方（承認後）

1. 表の migration・状態の型・受付の API（積むだけ。実行は偽物）。
2. worker と偽物の AI で、1 つのテンプレート（議事録）を最後まで通す。claim・再開・取消・世代のテスト。
3. 記事制作（お手本の抽出を含む）。
4. 帯・サイドバーの印・設定の「手順」の画面（#32・#33 の画面のあと）。
5. 本物のモデル（#38 の後段）と、必要なら予算の口（C）。

## 7. 決まったことと、既定で進めること

1. **方式**: **B（editor 専用）に決定**（オーナー 2026-10-31）。
2. 以下は**既定として進める**（異論があれば変える。実装の入口に 1 か所ずつ置くので、変更は小さい）。
   - **AI の費用の上限**: 未決。当面は #38 の月の上限（`EDITOR_AI_MONTHLY_LIMIT_USD`）を共有する。手順ごと・段階ごとの上限は、本物のモデルをつなぐ段で決める。
   - **通知**: v1 はブラウザ通知（許可したときだけ）。画面を閉じている間の通知（Web Push）は後。
   - **失敗時**: 自動の再試行は 3 回まで。再試行の前の通知は出さない（3 回とも失敗したら「失敗」として帯に出す）。
3. 非公開の NIHO の遠隔実行（A・C）とのつなぎは、必要になったときに別の Issue で。
